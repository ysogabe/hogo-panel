# 投薬予定の Mock API と画面評価 PRD

2026-10-22。[設計](design.md) / [配置検討](../CALENDAR_INTEGRATION.md)。

## 背景と目的

Google カレンダーの投薬予定は、hogo-meter が取得・設定・表示を担い、機器向け API でパネルへ配る方針に決めた（[配置検討](../CALENDAR_INTEGRATION.md#決定事項2026-10-22ユーザー確認)）。hogo-meter に手を入れる前に、本リポジトリの中で次の2つを評価する。

1. **API の評価:** パネルが受け取る応答の形（回の一覧、警告を始める日数、接続状態、表示のオン・オフ、エラー）が、パネルの表示に足りるか、扱いにくい点が無いか。
2. **画面表示の評価:** その API から取った予定で、Show 5 のパネルが正しく警告を出すか。hogo-meter ダッシュボードに足す予定の画面（カレンダーの接続設定、機器ごとの表示設定、直近の投薬予定）の見え方と、パネルとの違いが期待どおりか。

評価の結果を、hogo-meter 側の段階 A の PRD・設計の入力にする。

## 使う人と場面

- 開発者（ユーザー本人）が、PC で Mock API を起動し、ブラウザでダッシュボードの画面モックを操作しながら、ADB で繋いだ Show 5 の表示を確かめる。
- 家族向けの運用ではない。架空データだけを使う。

## ゴール / やらないこと

ゴール:

- PC で1つのコマンドで起動できる Mock API 兼ダッシュボードの画面モック。
- パネルが Mock API から予定を取り、今の操作モックと同じ警告・確認・取消の表示をする。
- API の形と評価の結果を文書に残す。

やらないこと:

- hogo-meter のリポジトリの変更。
- Google との実際の接続（OAuth、Calendar API の呼び出し）。接続は画面モック上の見せかけだけ。
- 「やった」・取消の API への送信。実施はこれまでどおりパネルのメモリ内だけ。このため、パネルで実施済みにしてもダッシュボードの予定は残る（今回の期待動作）。
- hogo-meter の機器登録・認証の実装。Mock API は起動ごとの評価用の値だけを確かめる。
- 薬ごとの警告日数、警告日数の編集画面、件名や色による予定の絞り込み。
- パネルの「今すぐ取得」メニュー（評価では取得間隔を短くして代える）。
- インターネット越しの接続。Mock API は PC の 127.0.0.1 だけで待ち受け、パネルは ADB のポート転送で届く。

## 要求

- **R1（必須）:** パネル向けの読み取り API を1つ定める。中身は、回ごとの識別子・系列・薬名・予定日、警告を始める日数、予定のタイムゾーン、接続状態、この機器での表示のオン・オフ、最後に取得できた時刻、次の取得までの間隔。どの過去の回まで返すかを決めて文書にする。形式は camelCase、時刻は epoch 秒（予定日だけは暦日の文字列）、エラーは JSON の `error` と HTTP ステータス、対象外のキーは省く。知らないキーは受け手が無視する。
- **R2（必須）:** Mock API は R1 の応答を返し、評価用の操作で次を切り替えられる: 予定の並び（普段・2日前・当日・超過・期限切れ・2種類同時・3種類同時・長い薬名・予定なし）、接続状態（正常・古い・未接続・再接続が必要・取得失敗）、機器の表示のオン・オフ、警告を始める日数、通信の失敗（認証エラー・サーバーエラー・応答の遅れ・壊れた応答）。予定日は、予定の並びを選んだ時点の日付（基準日）から作り、次に選び直すまで変えない。パネルは端末の本当の日付で判定する。
- **R3（必須）:** パネルは、接続設定を置いたときだけ Mock API から予定を取る（API モード）。設定が無ければ今の架空データの操作モックのまま動く。API モードでは、警告を始める日数は API の値を使い、コードの固定値を判定に使わない。
- **R4（必須）:** パネルは次の状態を、警告なしと区別して小さく出す: 未取得、通信できない、予定が古い、取得失敗、再接続が必要、カレンダー未接続、接続設定の誤り。通信できないときは最後に取れた予定で警告を続ける。成功していないものを「済」にしない。
- **R5（必須）:** パネルは、表示がオフの応答を受けたら薬カードと時計の薬名を出さない。ダッシュボードの画面モックでは、表示オフの機器が一目で分かる。
- **R6（必須）:** パネルは日付が変わったとき（時計を表示している間も含む）、警告を新しい日付で判定し直す。通信できない間も、最後に取れた予定で判定し直す。
- **R7（必須）:** 取得の結果を画面に反映するとき、押している途中の表示を変えない。開いている確認の対象（薬名と記録先）は変えない。無操作の時間を数え直さない。明滅と時計の薬名も結果に合わせる。
- **R8（必須）:** ダッシュボードの画面モックを、hogo-meter の見た目に寄せた静的 HTML（1ページで切り替え）で用意する: トップの「直近の投薬予定」、世帯の「カレンダー連携」設定（接続・切断の見せかけ、架空のカレンダー一覧からの選択、警告を始める日数の表示、接続状態）、デバイス詳細の「投薬の予定を表示する」のオン・オフ。画面モックの変更は、同じ Mock API の応答に反映される。
- **R9（必須）:** 評価用の切り替え欄を画面モックに付け、R2 の状態をブラウザから変えられる。パネルからの最近の要求（時刻・応答のステータス）も見られる。
- **R10（必須）:** API の形を文書にし、応答の見本を JSON ファイルとして置く。Mock API とパネルの両方のテストが同じ見本を使う。
- **R11（必須）:** 評価の手順と結果を記録する。Show 5 の実機での表示（スクリーンショット）、ブラウザでの画面モック、ブラウザとパネルの表示の対応、API で直したほうがよい点を残す。端末の識別子・アドレス・評価用の値など、公開してはいけない情報を記録に入れない。

## 受け入れ条件

- **AC1（R1, R10）:** API の文書に、各キーの型・意味・省略の条件・範囲、状態ごとの意味、過去の回の範囲、エラーのステータス、知らないキー・値の扱いが書かれている。見本の JSON（正常・古い・取得失敗・再接続が必要・未接続・表示オフ・エラー）がそろい、ID は架空と分かる形になっている。
- **AC2（R2, R10）:** Mock API の単体テストで、各評価状態の応答が見本と同じ形になる。基準日を固定して、予定の並びごとに返す回と、パネルが出すはずの警告（回と段階）が設計の表どおりになる。月末・年末・うるう日をまたぐ基準日でも正しい。127.0.0.1 以外では待ち受けず、Host・Origin の確認、静的ファイルの固定の一覧が効く。応答と状態の JSON に評価用の秘密の値が入らない。
- **AC3（R3, R10）:** パネルの単体テストで、見本の JSON を読み込み、回の一覧と警告日数が取り出せる。警告日数を3にした応答では3日前から警告が出る。壊れた JSON、深い入れ子、欠けたキー、型の違い、範囲外、重複した key、件数の超過で落ちず、取得失敗として扱う。おかしな回が1件だけなら、その回だけを除く。
- **AC4（R3）:** 接続設定が無い場合、今の単体テスト112件がそのまま通り、シナリオ選択の操作モックとして動く。
- **AC5（R4, R5, R7）:** 単体テストで次を確かめる: 初回の失敗では警告が無く「未取得・通信できない」が出る。成功の後の失敗では前回の予定で警告が続く。未接続では予定が消える。表示オフでは薬カードと時計の薬名が消える。確認を開いている間に予定が差し替わっても、題名と記録先が変わらない。差し替え後も実施済みが残る。押している途中に届いた結果は指を離してから反映される。無操作の時間が数え直されない。
- **AC6（R6）:** 単体テストで、時計の表示中に日付が変わると警告が「そろそろ」から「今日」に変わり、時計の薬名も更新される。通信できない間も同じ。
- **AC7（R7）:** 単体テストで、取得は同時に1件だけ、止めた後に届いた結果は捨てられ、止めている間は次の取得を予約しない。失敗の後は次の間隔で取り直し、成功すれば状態の表示が消える。
- **AC8（R8, R9）:** ブラウザで画面モックを操作し、カレンダーの選択・機器の表示のオン・オフ・評価用の切り替えが、パネルの次の取得で反映される（要求の一覧と実機で確認）。
- **AC9（R11）:** Show 5 の実機で、普段・2日前・当日・超過・期限切れ・2種類・3種類・長い薬名・表示オフ・未接続・取得失敗・通信できないの各表示をスクリーンショットで確かめ、ブラウザの表示との対応表と一緒に記録する。
- **AC10（R4）:** パネルが API モードでも、時計からの最初のタッチは復帰だけで、記録されない（既存の要件を壊さない）。単体テストを1件足す。

## 制約

- パネル: Android 11 の Show 5（960×480）、minSdk 30。AndroidX と実行時の外部ライブラリを使わない今の方針を守る。
- 常設の Show 5 には debug APK が入っており、Wi-Fi ADB も開いている。評価用の機能はこの前提で安全側に作る（[設計の安全面](design.md#安全面)）。
- 平文の HTTP は 127.0.0.1 と localhost だけに許し、debug ビルドに限る。接続設定は ADB の `run-as` で端末のアプリ専用領域に置き、ソースや APK や起動の引数に入れない。
- Mock API は PC 上で追加のインストールなしに動く（Python 3 の標準ライブラリだけ）。
- 公開リポジトリなので、hogo-meter のソースや本物の運用設定・認証方式を転載しない。データは架空のもの。

## 決まっていないこと

- 薬のアイコン（錠剤・滴下）をカレンダーの予定から決める方法。今回の Mock API は値を返すが、hogo-meter での決め方（色、件名、ダッシュボードでの系列ごとの設定）は評価後に決める。
- 実施の記録の共有。今回は実施を送らないため、過去の回は一定の日数（初期値 7 日）で API から外れ、未確認の警告もそこで消える。本来は hogo-meter に投薬の実施記録を持たせて解く（段階 B 以降）。
- 本番の機器認証の形（[配置検討](../CALENDAR_INTEGRATION.md#最大の未決事項-パネルを-hogo-meter-の機器としてどう認証するか)）。

# 投薬予定の Mock API と画面の評価記録

2026-10-22 14:51〜15:04（JST）、追加の確認 15:07〜15:10。[PRD](prd.md)（R11・AC8・AC9）/ [設計](design.md) / [API](api.md)。パネルを Mock API につなぎ、実機（Show 5）とブラウザで表示を確かめた記録。データはすべて架空（ペット名「こむぎ」、架空の薬名・予定・時刻）。

## 目的

- API v0 の形が、パネルの表示に足りるか、扱いにくい点が無いかを確かめる（PRD の評価 1）。
- その API から取った予定で、パネルが正しく警告・状態を出すか、ダッシュボードの画面モックとの違いが期待どおりかを確かめる（PRD の評価 2）。
- 結果を、hogo-meter の段階 A の PRD・設計の入力にする（[引き継ぎ](../CALENDAR_INTEGRATION.md#mock-での評価2026-10-22)）。

## 手順

[Mock API の README](../../tools/mock-hogo-meter/README.md) のとおり。

1. `python3 tools/mock-hogo-meter/server.py` を起動する。
2. `date` と `adb -s <アドレス>:5555 shell date` で PC と端末の日付を確かめる。
3. `adb -s <アドレス>:5555 reverse tcp:8787 tcp:8787`。
4. `tools/mock-hogo-meter/push-config.sh <アドレス>:5555 <設定ファイル>`。`-rw-------` の `api-config.json` が出ることを確かめる（中身は見ない）。
5. `am force-stop` の後に `am start`。Mock の要求の一覧に `GET /api/agent/mock-panel-1/medications` が 200 で出る。
6. 状態は 8788 の `POST /mock/state`（`Origin: http://127.0.0.1:8788` と `Content-Type: application/json` が要る）で切り替える。パネルの次の取得（15 秒ごと）の後に `screencap` で撮る。
7. パネルは無操作で 3 分後に時計へ変わる（評価中は状態の切り替えを待つ間に何度も時計になった）。2 回目以降は、ヘッダーの空き（480,40）をタップして起こしてから撮った。時計からの最初のタッチは復帰だけで、記録も確認も起きなかった（AC10 を実機でも観察。画像なし）。

## 判定

- **AC8（ブラウザの操作がパネルの次の取得で反映）: 満たす。**
  - 機器の表示のオン・オフは、ブラウザのスイッチを実際にクリックして確かめた（`b2p-enabled-on`）。
  - 追加の確認（0.3.0）で、ブラウザの切り替え欄の「予定の並び」を `soon`、「接続状態」を `stale` に選び、カレンダー連携で「家族」（`mock-cal-2`）をクリックした。Mock の状態が変わり、`/mock/preview` の `key` が `occ-cal2-…` に変わり、パネルの次の取得で「そろそろ」と状態の行「予定が古い」が出た（`b2p-browser-switches`）。
  - 個々の状態の網羅（警告日数・`fault`・表示オフなど）は、同じ `POST /mock/state` を curl で送って確かめた（上の表）。画面モックも同じ API を呼ぶ。
  - 要求の一覧は、パネルの取得（200）と、`fault` の間の状態を見るのに使った。
- **AC9（実機での各表示）: 満たす。** 普段・2日前・当日・超過・期限切れ・2種類・3種類・長い薬名・表示オフ・未接続・取得失敗・通信できない（初回／取得後）の各表示を撮り、上の表のとおり期待と一致した。ブラウザとの対応表も上にある。
- **AC10（時計からの最初のタッチは復帰だけ）: 実機でも観察。** 記録も確認も起きなかった。画像は撮っていない。単体テストでも確かめている。

## API・画面で直したほうがよい点（R11）

段階 A で決めるか、段階 B の API・パネルに反映する。

1. **「予定を取得できません」と「予定を更新できません」が似ている。** 前者はパネルが API に届かない、後者はサーバーが Google から取れない。利用者のすることが同じなら 1 つにまとめる。違うなら文言を分ける（例: 後者を「カレンダーから更新できません」）。「予定を未取得（通信できません）」も含めて整理する。
2. **長い薬名はカードで 8 文字ほどしか見えない。** 予定の件名を短くする運用（12 文字程度）をダッシュボードで案内するか、API に表示用の短い名前を足すかを段階 A で決める。
3. **実施を送らないので、ダッシュボードには実施済みの回も残る。** 今回の期待どおり。`am force-stop` でパネルの実施済みも消える。本番には投薬の実施記録が要る（PRD の「決まっていないこと」）。
4. **`fault` は表示オフより先に効く。** 要求の一覧の 200 は、パネルが採用したことを意味しない（壊れた JSON も 200）。評価の手順で注意する（[README](../../tools/mock-hogo-meter/README.md#fault-ごとのパネルの結果)）。
5. **状態の行（terracotta）の読みやすさ。** 実機のスクリーンショットでは読めるが、肉眼の距離では未確認。
6. **無操作で 3 分後に時計に変わる。** 評価の手順は「起こしてから撮る」が要る（手順 7）。
7. **カレンダーを切り替えると、実施済みが外れて警告が戻る。** `key` にカレンダーが入る（設計どおり）ので、「家族」で「やった」（`b2p-done-on-cal2`）にしてから「ねこの投薬」に戻すと、同じ薬の「そろそろ」が出た（`b2p-calendar-switch-after-done`）。本番で使うカレンダーを変えたときの実施記録の扱い（引き継ぐか、変えた時点で切り替えるか）を段階 A・B で決める。

## 画像の確認

30 枚（実機 27 枚、ブラウザ 3 枚）をコミットの前に目で確かめた。

- 実機の画像に写っているのは、架空のペット名「こむぎ」、架空の薬名、時刻と日付、お世話の経過時間だけ。端末のアドレス・シリアル、評価用の値、PC の情報は無い。
- ブラウザの画像に写っているのは、画面モックのページ部分だけ（アドレスバー・タブ・PC の情報は無い）。架空の機器 ID（`mock-panel-1`）、架空のカレンダー ID（`mock-cal-1`・`mock-cal-2`）、架空のデバイス名、パネルからの要求（時刻・パス・ステータス）が出る。評価用の秘密の値は画面に出ない設計。
- PNG のメタデータに端末や PC の情報は無い（実機は `sRGB`・`sBIT`、ブラウザは付加情報なし）。

## 片付け

- `adb reverse --remove tcp:8787` で転送を外した。
- 端末の `files/api-config.json` を削除した（`run-as … rm`）。
- Mock を停止した（接続設定の一時フォルダも消えた）。
- アプリを `am force-stop` の後に再起動し、設定なし（シナリオの操作モック）に戻した。

# Google カレンダー連携の配置検討（PoC 前）

2026-10-21。操作モック（0.2.3）の次段として、投薬予定を Google カレンダーから取る PoC の実装場所を検討した。まだ実装していない。連携元 hogo-meter は default branch `main` の `c6c14d6b60144d1ccffeb279706a35834b68d313` を参照した（非公開。[連携の引き継ぎ](HOGO_METER_INTEGRATION.md#参照先)と同じ）。

## 前提

- 接続先は Google カレンダー。
- 接続・カレンダーの選択・表示の有無は **hogo-meter 側で設定できる** ようにしたい（ユーザー要望）。
- パネルは投薬の「2暦日前から警告」を出す（[PRD](routine-ui/prd.md)）。今は `PanelModel` の架空データ（`Scenario`）で動いている。

## 結論: Google との接続は hogo-meter のダッシュボードに置く

```
Google Calendar API
   │  OAuth（世帯ごと・読み取りのみ）
   ▼
hogo-meter ダッシュボード（Next.js）
   ├─ 世帯の設定: Google 接続、使うカレンダーの選択
   ├─ 機器の設定: このパネルに投薬警告を出すか
   ├─ 予定の取得・キャッシュ・正規化（回ごとのキー・日付・薬名）
   └─ 機器向け API で「回の一覧」を配る
        │  HTTPS（既存の機器 API と同じ経路と認証）
        ▼
hogo-panel（Show 5）
   └─ 回の一覧を受け取り、2暦日前の判定・表示・「やった」を担う（ReminderPolicy は今のまま）
```

理由:

1. **設定を hogo-meter で行うという要望に合う。** パネルが直接 Google に繋ぐと、接続も選択もパネルの小さな画面で行うことになる。
2. **Google の資格情報が端末に載らない。** refresh token はサーバーにだけ置く。共有の常設端末や、公開リポジトリから作る APK に Google の秘密を入れずに済む。
3. **既存の仕組みに乗る。** hogo-meter には、世帯ごとの設定、機器ごとの設定を機器へ配る仕組み、アプリ内の定期処理が既にある。カレンダーも同じ形で足せる。
4. **他の画面にも出せる。** ダッシュボードや他の hogo-meter 端末で「次の投薬」を出すときも、同じ正規化済みデータを使える。

パネル側に残すもの: 2暦日前・当日・未確認の判定（[`ReminderPolicy`](../app/src/main/kotlin/io/github/ysogabe/hogo/panel/ReminderPolicy.kt)）、表示、確認と取消。予定の取り方だけを `ScheduleSource` として差し替える（[設計](routine-ui/design.md#既存コードと将来の連携)のとおり）。

採らない案:

- **パネルが直接 Google に繋ぐ:** hogo-meter で設定・選択できない。端末に refresh token を置くことになる。
- **hogo-meter が設定だけ持ち、token をパネルへ配る:** 秘密が端末へ流れるので、1 より悪い。

## Google への接続方式

推奨: **世帯ごとの OAuth（ダッシュボードの「Google と接続」ボタン）で、読み取り専用のスコープだけ** を使う。

| 方式 | 資格情報の置き場所と世帯の分離 | 繰り返し予定（毎月の薬） | 手間 | 判断 |
|---|---|---|---|---|
| 世帯ごとの OAuth | 世帯ごとの refresh token をサーバーに保存。他の世帯のカレンダーは読めない | `events.list` の `singleEvents=true` で回ごとに展開され、回ごとの ID を `occurrenceKey` に使える | Google Cloud のプロジェクトと同意画面の設定が要る | **採用** |
| 非公開の iCal アドレス（秘密の URL） | 世帯ごとの URL をサーバーに保存。URL がそのまま資格情報 | RRULE を自前で展開する必要がある | Google Cloud の設定が要らず最も手軽 | OAuth が詰まったときの PoC 用の代わり |
| サービスアカウントへカレンダーを共有 | 全世帯で1つの資格情報。カレンダー ID を入力されれば、そのサービスアカウントに共有済みの他世帯のカレンダーも読めてしまう | OAuth と同じ | 中 | 世帯をまたいで漏れる経路があるため採らない |

スコープはカレンダー一覧の読み取り（選択画面用）と予定の読み取りに絞る（例: `calendar.calendarlist.readonly` と `calendar.events.readonly`。実装時に Google の最新の一覧で再確認する）。書き込みはしない。

注意（2026-10-21 に Google の OAuth 文書で確認）: 同意画面が外部ユーザー向けで公開ステータスが「テスト」の場合、refresh token は **7日で失効** する。PoC では週に1回の再接続を受け入れるか、テスト用 Google アカウントで試す。カレンダーのスコープは機密スコープに当たるため、本番運用に出すには Google の確認（審査）が必要になる。PoC の範囲外として残す。

## hogo-meter 側に足すもの（PoC）

設定の単位は、既存の通知設定と同じく「世帯」と「機器」に分ける。

- **世帯の設定（新しい設定画面。例: `/settings/calendar`、admin のみ）:** Google と接続・切断、使うカレンダーを1つ選ぶ（投薬専用カレンダーを推奨）、接続状態（未接続・正常・認可切れ・取得失敗）の表示。
- **機器の設定（デバイス詳細）:** 「投薬の予定を表示する」のオン・オフ。
- **ダッシュボードでの表示:** 直近の投薬予定（薬名と日付）を一覧で出す。パネルが無くてもブラウザで確認できる。
- **取得とキャッシュ:** 予定はサーバーが取り、DB にキャッシュする。取りに行くのは、既存のアプリ内の定期処理に相乗りする方式（例: 10分ごと）か、要求時にキャッシュが古ければ取り直す方式。Google には今日の前後（例: 過去14日〜先60日）だけを、必要な項目（ID・件名・開始日）だけ要求する。
- **機器向け API:** 頻繁に呼ばれる既存の設定取得には予定の本体を載せない。別の機器向けエンドポイント（例: 投薬の回の一覧）を用意し、パネルは数分おきに取る。既存の設定取得には変更の目印（版の番号）だけを載せる形でもよい。
- **配る内容:** 回ごとに `occurrenceKey`（カレンダー ID と回の ID から作る）、薬名（予定の件名）、予定日（現地の日付）、取得時刻。未取得・古い・認可切れはパネルが区別できる状態値で返す。

時刻の基準: 予定日は **選んだカレンダーのタイムゾーン** での日付としてサーバーが決めて配る。パネルは端末の現地日付と比べて2暦日前を判定する（Show 5 と世帯のタイムゾーンが同じ前提。違う場合は後で世帯の設定を足す）。

## hogo-panel 側に足すもの（PoC）

- `ScheduleSource` の実装を、架空データから hogo-meter の機器向け API に差し替える。取得失敗・古い情報・認可切れは、警告なしと区別して小さく出す（成功していないものを「済」にしない）。
- 「やった」は PoC では今と同じくパネルのメモリ内だけ。本来の置き場所は hogo-meter の **投薬の実施記録（日々のお世話の記録とは別）** で、家族や他の端末と共有するときに追加する（PRD の R5 のとおり、お世話の項目へは自動記録しない）。
- 初めてのネットワーク機能になるため、INTERNET 権限と HTTPS 通信を追加する。

## 最大の未決事項: パネルを hogo-meter の機器としてどう認証するか

機器向け API は、経路の保護と機器ごとの認証の二層になっている。詳細は連携元の文書（参照コミット）を正とし、ここには転載しない。パネル側には次の制約がある。

- 共通の資格情報を APK に入れられない（公開リポジトリから作る。[引き継ぎ](HOGO_METER_INTEGRATION.md#実装前に決めること)の方針）。パネルの設定画面か ADB で初回に入れ、端末のアプリ専用領域に保存する。
- Android 11 のアプリは本物の MAC アドレスを読めない。端末固有の ID が登録に要るなら、初回起動時に乱数の ID を作って保存し、画面に出す方式が要る。
- パネルは hogo-meter の機器の種類として登録されていない。hogo-meter 側に種類（例: `hogo-panel`）の追加が要る。

これは [引き継ぎ](HOGO_METER_INTEGRATION.md#実装前に決めること) の 2〜4（既存デバイスの記録を操作するか、新しい端末として登録するか、利用者向けと機器向けの認証の区別）とまとめて決める必要がある。

## 進め方（推奨）

1. **段階 A（hogo-meter だけ）:** Google との OAuth 接続、カレンダーの選択、予定の取得・キャッシュ、ダッシュボードでの直近の投薬予定の表示。ブラウザだけで確かめられ、パネルの認証の問題と切り離せる。テスト用の Google アカウントと投薬専用カレンダーで行う。
2. **段階 B（両方）:** パネルの機器登録（上の未決事項を決める）、機器向けの回の一覧 API、パネルの `ScheduleSource` の差し替え、機器ごとの表示のオン・オフ。

## 決定事項（2026-10-22、ユーザー確認）

- **進め方:** 上の段階 A → 段階 B のとおり。段階 A は hogo-meter のリポジトリで PRD・設計から始める。
- **表示の選択:** 使うカレンダーの選択、機器ごとの表示のオン・オフ、hogo-meter のダッシュボードでの直近の投薬予定の表示、の3つを行う。
- **どの予定を薬とみなすか:** 初期 PoC ではカレンダーの使い方をこのアプリに合わせる。**投薬専用のカレンダーを1つ作り、その中の予定はすべて薬とみなす**（カレンダーそのものをカテゴリとして使う）。件名が薬名、予定日が投薬日。終日の予定で、毎月などの繰り返しを推奨する。件名の解析や色による絞り込みはしない。
  - Google カレンダーの予定には汎用のカテゴリ欄が無い。色（`colorId`）は11色の見た目用の値で意味が決まっておらず、アプリが付ける拡張プロパティは Google カレンダーの画面から編集できない。専用カレンダーなら画面から迷わず登録でき、取得側も絞り込みが要らない。
  - 色や件名の目印で1つのカレンダーから選び分ける方式は、必要になったら後で足す。
- **警告を始める日数:** 初期 PoC では薬ごとに変えない（全薬共通で2暦日前）。ただし値をコードに直接書かない。hogo-meter が世帯の設定値（初期値2、PoC では編集画面なし）として持ち、ダッシュボードの判定とパネルへの配信の両方でこの値を使う。パネルの今の固定値 `ReminderPolicy.WARN_DAYS_BEFORE` は、段階 B で配信された値を使う形に置き換える。

## Mock での評価（2026-10-22）

hogo-meter に手を入れる前に、本リポジトリの Mock API（`tools/mock-hogo-meter/`）とパネルの API モード（0.3.0）で、機器向け API の案（v0）と画面の表示を評価した。[PRD](calendar-mock/prd.md) / [設計](calendar-mock/design.md) / [API](calendar-mock/api.md) / [評価記録](calendar-mock/verification.md)。

- **評価の要約:** Hogo Panel 用の Show 5（Wi-Fi ADB）とブラウザの画面モックで、普段・2日前・当日・超過・期限切れ・2種類・3種類・長い薬名・古い・更新できない・再接続が必要・未接続・表示オフ・認証エラー・壊れた応答・サーバーエラー・通信の切断と回復を確かめた。どれも期待どおりに表示された。ブラウザのスイッチで機器の表示をオン・オフすると、パネルの次の取得で反映された。スクリーンショットと対応表は [verification.md](calendar-mock/verification.md)。
- **API v0 の形で足りたこと:** 回の一覧（`key`・`seriesId`・`name`・`date`・`icon`）、`leadDays`、`status`、`enabled`、`timeZone`、`pollSeconds` だけで、評価した全部の表示を出せた。警告を始める日数はコードに直書きせず、応答の値（2 と 3 で確認）を使えた。表示オフと未接続は別の応答の形で、パネルは警告を消せた。成功していない取得を「済」にせず、前回の予定で警告を続けられた。`key` が差し替えをまたいで変わらない前提で、実施済みが残った。
- **API・画面で直したほうがよい点（段階 A・B で決める）:**
  1. 「予定を取得できません」（パネルが API に届かない）と「予定を更新できません」（サーバーが Google から取れない）が似ていて区別しにくい。利用者のすることが同じなら 1 つにまとめる。違うなら文言を分ける（例: 後者を「カレンダーから更新できません」）。
  2. 長い薬名はカードで 8 文字ほどしか見えない。予定の件名を短くする運用（12 文字程度）をダッシュボードで案内するか、API に表示用の短い名前を足すかを段階 A で決める。
  3. 実施を送らないので、ダッシュボードには実施済みの回も残る。本番には投薬の実施記録が要る（段階 B 以降）。
- **未確認:** 実際の 0 時またぎ（単体テストだけ）、`fault=slow` の実機での `TIMEOUT`、長時間の連続動作、肉眼での見え方、Google・hogo-meter・機器認証・HTTPS との実際の接続。

## 本番（hogo-meter の段階 A・B）へ引き継ぐ注意

Mock は評価用で、本番の認証・機器登録の実装ではない（詳細は [設計の安全面](calendar-mock/design.md#安全面)）。本番では次を守る。

- **設定の受け渡し:** 起動 intent や exported な受け口で接続先や資格情報を設定する経路を持ち込まない。常設端末で debuggable なビルドと TCP ADB を併用しない。Mock の `run-as` で置く設定ファイルは評価用の方法で、本番の初回設定の方法ではない。
- **資格情報:** 機器ごとに失効・更新できるものにし、共有の値を全機器で使わない。資格情報（ヘッダーの値を含む）をサーバーのログ・応答・状態に出さない。本番では localhost の平文に秘密を載せず、HTTPS にする。
- **認証の失敗:** リダイレクトやログイン画面の HTML が返る場合も、取得失敗として扱う（パネルはリダイレクトを追わず、200 以外の本文を読まない）。
- **警告が消える方向の状態:** 表示オフ（`enabled:false`）と未接続（`notConnected`）はパネルの警告を消す。ダッシュボードで、表示オフの機器と未接続を目立たせる。評価の画面モックでは、機器カードを赤枠にして確かめた。
- **実施の送信（段階 B 以降）:** 冪等キーを付け、自動で送り直さない（[KNOWLEDGE_HANDOFF.md](KNOWLEDGE_HANDOFF.md)）。`key`（occurrenceKey）が同じ回なら、再取得・件名の変更・予定日の移動をしても変わらないことを、Google の回の ID で確かめる。
- **公開してよい記録だけ:** 端末のアドレス・シリアル・資格情報・hogo-meter の非公開の情報を、文書・スクリーンショット・Issue に残さない。
